# AG-018: Worker and internal TTS integration

This records the original AG-018 implementation/acceptance. AG-019 replaces the named `voice` request with a required database `voiceId`, a seeded voice catalog and plan/revocation checks; see [AG-019](AG-019.md) for the current request and seed/migration contract.

The real `.env` files have not been changed for AG-018. The earlier env audit was rolled back and deleted variables restored from original snapshots.

## Workflow and API

1. `POST /api/scenes/:id/tts` requires the user's access-token cookie, matching CSRF cookie/header, and `Idempotency-Key` (8..128 ASCII letters, digits, underscore, period or hyphen). Body: `{ "voice": "Hải Đăng" }`, optional voice defaults to that local preset. The server reads narration from the owned scene, never a client-supplied URL or arbitrary provider request.
2. Response: `202 { success: true, data: { jobId, status, reservedCredits, reused: false } }`. A repeated key with the same scene/voice returns the same job with `200` and `reused: true`; changing scene/voice with that key returns `409 IDEMPOTENCY_CONFLICT`.
3. MongoDB creates Job(type TTS) and reserves credit in one transaction. Repeated keys are scoped to owner. Default TTS pricing is 1 credit per started 100 Unicode characters; `SystemSettings.TTS_CREDITS_PER_100_CHARS` overrides the positive integer rate for new jobs. The computed cost and scene revisions are snapshotted on the job. Input is limited to 3000 UTF-16 code units; voices must be valid local presets. Insufficient credit returns 402; missing provider configuration returns 503 before creating a job or holding credit.
4. The separate `apps/worker` process claims durable Mongo TTS jobs using a 120-second lease and UUID execution fence, renews the lease every 30 seconds, and handles one job at a time. A crashed worker's expired lease can be reclaimed; at most 3 claims are allowed. This TTS queue uses Mongo jobs directly; it does not depend on the existing Redis mock queue used for AI_CONTENT. The old worker was a no-op Redis consumer; it now runs the real TTS worker exported by backend-api.
5. Only Worker calls internal `POST /synthesize`. The Python service requires a shared bearer token, binds to loopback by default, has no permissive CORS, loads all model artifacts locally, and never invokes download_models.py from requests. Provider configuration rejects public hosted URLs; use loopback/private IP or an internal service DNS name.
6. TTS response must be `audio/wav`; its stream is capped at 32 MiB. The RIFF/WAVE parser verifies complete chunk bounds, PCM format, sample rate/channels/block alignment and duration 0.1..300 seconds. Timeout is 120 seconds per request, max 3 attempts, with bounded backoff; only network/timeouts/429/5xx retry. Other provider/auth/format errors are terminal.
7. Worker uploads to Cloudinary as `resource_type=video`, `type=authenticated`, using a signed request and deterministic job public ID with `overwrite=false`. Upload has a 60-second timeout and max 2 attempts. It downloads and validates the actual authenticated object before publishing; replay after a lost upload response reuses the existing object.
8. One Mongo transaction writes `media_assets`, updates `scene.ttsAudioId`, settles the held credit and marks the fenced job COMPLETED. It rechecks scene/content revisions and ownership before publication. Terminal failure atomically releases credit and marks FAILED. Credit reserve/settle/release are idempotent and can share the caller transaction. A stale worker cannot settle/refund/publish or delete a newer worker's asset. Failed uploaded files are destroyed; cleanup failures are recorded and retried at most 3 times.
9. `GET /api/jobs/:id` retains the existing owner-only polling contract. A completed TTS result contains `audioId`, `sceneId`, `audioUrl`, `contentType`, `duration`, `bytes`, `chargedCredits`. `audioUrl` is the backend path `/api/media/:id/audio`.
10. `GET /api/media/:id/audio` requires authentication and checks the media owner and live project. It fetches a short-lived signed Cloudinary download on the backend, verifies the stored SHA256, and serves WAV with `Cache-Control: private, no-store`. Neither Cloudinary signed URLs nor TTS URL/token are returned to the client. Other owners receive 404.

## Configuration and startup

Add to the service process environment (examples are appended; real env values are preserved):

| Variable | Required by | Meaning |
| --- | --- | --- |
| `TTS_SERVICE_URL` | API and Worker | Internal origin, e.g. loopback port 8001; no public TTS API |
| `TTS_SERVICE_TOKEN` | API, Worker and Python TTS | Same secret on these processes, at least 32 printable ASCII characters; never VITE_ |
| `MONGODB_URI` | API and Worker | Existing Mongo replica set for transactions |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | API playback and Worker upload | Existing Cloudinary authenticated storage credentials |
| `TTS_BUNDLE_PATH` | Python | Existing absolute local artifact directory; defaults to artifacts beside service code |

Worker reads its own `.env` if present, then backend `.env` for absent values; injected process environment takes precedence. Python uses its process environment, not automatic `.env` loading. Generate the shared token privately and configure the service supervisor; do not print it in shell logs or commit it.

```powershell
pnpm -r run build
services/tts/.venv/Scripts/python.exe services/tts/launch.py
pnpm --filter @creatorai/worker start
pnpm --filter @creatorai/backend-api start
```

Set the variables above before starting. The API never performs TTS inference. Backend can also run the worker with `pnpm --filter @creatorai/backend-api worker:tts`. Both worker commands are alternatives; run one instance for this local CPU configuration. For a controlled diagnostic of an existing job, `node apps/backend-api/dist/workers/tts.js --job-id JOB_ID` claims/processes only that job and exits.

Python inference requires no Internet and all weights remain local. Upload and playback through Cloudinary require Internet; this does not change the offline inference requirement. No dependency/model installation is performed during a request.

## Verification

Provider and worker tests cover WAV size/format/duration, MIME rejection, timeout signals, bounded retry, authentication, signed authenticated uploads, short-lived delivery, fenced publication, stale scenes, retry exhaustion and one credit settlement/refund.

`node apps/backend-api/scripts/test-tts-local.cjs` uses the actual Python ONNX model, a separate Node Worker, a real Mongo transaction/unique indexes and real Cloudinary authenticated upload/delivery. It creates temporary users/scenes/wallets only, verifies repeated request/completion/refund behavior and protected playback, saves the downloaded WAV/report under `services/tts/offline-output/ag018`, then deletes its Cloudinary asset and exact Mongo fixtures. Test credentials are injected only into child process environments.

The saved `acceptance.json` reports the measured bytes/duration/sample rate/non-silent peak and full-flow checks. `worker-playback.html` and `worker-playback.wav` allow listening to the audio downloaded through authenticated backend playback. Windows playback verification is recorded separately.

Final local results: monorepo build and configured typechecks PASS; 45 provider/worker/content/project tests PASS. Four simultaneous creation requests produced one job/hold; real synthesis/upload/protected download and replay/refund checks all PASS, with fixture cleanup confirmed. The downloaded WAV is 445484 bytes, 4.64 seconds, mono PCM16 at 48000 Hz; Windows SoundPlayer Load/PlaySync PASS is saved in `playback.json`, bound to its SHA256. `node apps/backend-api/scripts/test-credit-expiry-local.cjs` also passed real-Mongo expired-credit settlement/release replay and ledger reconciliation using isolated fixtures.

The updated Python service restarted and synthesized twice from the verified backup under Windows outbound firewall blocking; GitHub, Hugging Face and author-host negative probes were blocked. See `services/tts/offline-output/service-test.json` and `firewall-admin.log`. This certifies the tested Windows CPU local inference configuration; Cloudinary upload/playback still requires Internet. Backup inventory verified all 5991 files after the service authentication update.
